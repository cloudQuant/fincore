## 1. 目标分支语义和目标工作流

### 1.1 D0 推荐值：候选 B

推荐将 master 定义为唯一权威发布线和日常贡献入口，dev 定义为受限的集成预演线。选择它的原因是当前默认分支、CI 入口、发布工作流和 master/dev 同步状态均已与此方向一致，迁移成本最低。

| 分支 | 允许进入的变更 | 进入方式 | 离开/同步方式 | 禁止事项 |
|---|---|---|---|---|
| master | 一般贡献、修复、文档、已完成的高风险变更、发布候选 | feature/* 到 master 的 PR；无直接 push | 发布从此分支的已验证候选产生；向 dev 同步只能走 PR | 不接受未经完整验证的集成试验。 |
| dev | 仅有已登记 issue/ADR 的跨模块、依赖升级或大特性预演 | integration/* 到 dev 的 PR；PR 必须列明集成票据、预计晋升日期和回滚点 | master 到 dev 同步 PR；达到出口条件后 dev 到 master promotion PR | 不发布、不作为默认贡献入口、不无限期保留仅存在于 dev 的变更。 |
| origin/gh-pages | 既有遗留部署历史 | 本迭代不写入 | 仅在独立 Pages 迁移计划中处理 | 不作为源码、审查或当前文档产物分支。 |

dev 中任何未晋升差异的最长存续期为 14 个自然日或下一个发布候选评审日（先到者）。届时必须 promotion、明确放弃，或先通过 master 到 dev 同步 PR 解决分叉；不得通过 force push 重置受保护分支。

候选 A 仍可选择：dev 为日常贡献入口、master 为稳定发布线，全部常规变更经 dev 到 master promotion PR。若选择 A，管理员必须同时决定默认分支是否改为 dev；若保留 master 为默认分支，CONTRIBUTING、PR 模板和分支选择链接必须明确说明该例外。候选 A 不得只“反转箭头”而遗漏 CI、文档和发布责任。

### 1.2 工作流

    普通变更：
    feature/* -- PR + R0/R1 验证 --> master

    例外集成：
    integration/* -- 关联 issue/ADR + R2/R3 验证 --> dev
    dev -- promotion PR（完整验证、差异/回滚说明） --> master
    master -- 同步 PR（仅为保持集成线新鲜） --> dev

    安全问题：
    私密渠道 -- 最小修复 PR + R3 门禁 --> D0 确认的主贡献分支

    发布：
    master 上与成功 CI 同 SHA 的候选工件 --> 现有 publish.yml 验证 --> PyPI 环境人工批准

### 1.3 PR 目标分支和风险决定表

| 情况 | 候选 B 的默认目标 | 最小证据 | 合并后动作 |
|---|---|---|---|
| 文档、示例、非行为性工具 | master | 受影响文档构建或静态检查 | 进入下一个候选集。 |
| 局部功能/修复，未改变公开行为或数值算法 | master | 回归测试与 R1 验证 | 进入下一个候选集。 |
| 公开 API、严格兼容 façade、数值内核、冻结清单或跨模块集成 | master；只有登记过的预演才可例外进入 dev | R2/R3 验证、必要 ADR、API snapshot 和 oracle/property 证据 | 如在 dev，必须走 promotion PR 后才能发布。 |
| 破坏性公开 API | master，且不得绕过 ADR | ADR、SemVer/弃用窗口、API snapshot 差异报告 | 写入 CHANGELOG 的 breaking 区块；不因 PR 合并改变 readiness seal。 |
| 安全/供应链/发布配置 | D0 主贡献分支；先走 D6 私密渠道 | 最小复现、修复回归、R3 清单 | 不在公开 issue 泄露细节；所有 bypass 留痕。 |

## 2. 风险级别与可执行门禁

路径只能给出下限；任何改变结果、公开行为、依赖供应链或发布权限的改动都必须升到对应等级。不能因 diff 小、测试数量多或作者熟悉模块而降级。

| 等级 | 典型范围 | 最低评审 | 最低验证 |
|---|---|---|---|
| R0 文档/元数据 | 普通 docs、mkdocs_docs、示例、非策略性的 Issue Form/PR 文本 | 1 位维护者 | 受影响文档 strict build 或静态检查。 |
| R1 局部实现 | 无公开行为变化的局部测试、非数值工具、单后端展示代码 | 1 位模块 owner | 定向回归 + fast suite。 |
| R2 行为/兼容/数值 | fincore/empyrical.py、fincore/pyfolio.py、fincore/alphalens/、fincore/factor_analysis/、fincore/core/、fincore/_dispatch.py、fincore/_registry.py、fincore/contracts/、任何改变计算结果的 fincore/metrics/ 代码、tests/compat/fixtures/ | code owner + 独立维护者；独立维护者缺失时走 D3 临时例外 | 全量 CI；compat、numerical、oracles、property；当前 0.4 API snapshot；必要 ADR。 |
| R3 安全/治理/发布/供应链 | .github/workflows/、.github/CODEOWNERS、.github/governance/、publish.yml、pyproject.toml、setup.py、requirements/constraints、许可证/notice、私密安全修复 | 核心维护者明确批准；涉及 R2 时叠加其证据 | 目标分支完整 CI、打包/发布相关检查、人工变更审查和回滚记录。 |

R0 不包括 Actions workflow、CODEOWNERS、Ruleset manifest、发布/安全策略；这些文件即使只有一行改动也至少是 R3。metrics/ 下只要改动数值公式、边界条件、输入清洗或输出投影，即为 R2。

## 4. 原生规则、自动化和人工责任的边界

| 控制项 | 实现位置 | 不应作出的错误承诺 |
|---|---|---|
| 禁止 force push、删除、直接更新；要求 PR、1 个批准、最新提交复审、解决会话 | GitHub Ruleset | 不能把没有任何实际设置的 JSON manifest 当成已生效保护。 |
| 路径 owner 复审 | CODEOWNERS + Ruleset 的 require code-owner review | 一个文件若有多个 owner，任一 owner 批准即可；它不天然等于“两名独立维护者”。 |
| R2 路径识别、风险标签建议、fixture/API evidence 声明 | 无路径过滤的 PR Governance / policy workflow；现有 CI / build 独立执行 C0-C4、数值和 property 门禁 | workflow 不能仅凭 PR 模板复选框证明数值正确；policy 与 CI / build 必须同时成为 required checks。 |
| R2 独立复审与单维护者例外 | GitHub review 事件 + policy check + issue/PR 审计记录 | User-owned 仓库不能假设存在组织 Team 的按路径 required reviewer；管理员 bypass 也不能被伪装成正常审批。 |

PR Governance workflow 必须使用 pull_request，最小权限为 contents: read、pull-requests: read、checks: read。它不得使用 pull_request_target，不得检出或执行来自 fork 的代码后再访问 secrets，也不得因 fork 默认只读 token 无法打标签/评论而把标签写入当成强制机制。

### M4：分阶段应用 Rulesets，并完成真实 PR 演练

**优先级：P0；负责人：仓库管理员 + CI owner；依赖：M2、M3 已合入 master 且有成功 CI。**

**步骤：**

1. 在一个由 fork 发起的 R0 PR、一个常规 R1 PR、一个触碰兼容/数值路径的 R2 PR 上采集 check-runs、review request、CODEOWNERS 与 policy 输出。记录完整 context 名称、执行 app id、head SHA 和结果。
2. 把 M2 中 pending-evidence 的 context/app id 替换成真实值，运行离线比较器；只有此时 manifest 才可部署。
3. 先进行两周 report-only 观察。若当前 GitHub UI/API 没有适用于本仓库的 evaluate 状态，则不假装存在“观察 Ruleset”：保持 Ruleset 未启用，只运行 report-only policy 并记录误报/漏报。

6. 若 D3 仍为单维护者例外，至少演练一次合规例外；报告必须将其标注为风险接受，不得写成第二位审查者已存在。

**退出条件：** 三类 PR 的路由、checks、owner request、阻塞和例外处理都符合 D0-D4；设置已通过 API 和离线比较器双重证明，而不是只凭 UI 截图。

## 8. 主要风险与回滚原则

| 风险 | 防护 | 回滚/处置 |
|---|---|---|
| D0 不决导致 dev 再次无定义分叉 | D0 是 M1-M4 的硬前置；记录临时决定与复审日 | 不启用 Ruleset，只保留 M0 证据。 |
| required workflow 被 paths/branch filter 跳过 | PR Governance 无 paths filter；在启用前采集真实 check-runs | 立即 disabled 新 Ruleset，修复 workflow 后重新演练。 |
| job id 与实际 required check context/app id 不同 | M2 允许 pending-evidence；M4 从 API 采集 | 不启用或回退 settings，不靠管理员 bypass。 |
| 单维护者把自身 PR 当作“双人审查” | D3 明确风险接受、24 小时冷静期、例外记录和到期日 | 关闭/延后高风险 PR，或以管理员例外留痕；不虚构 reviewer。 |
| PR 自动化因 pull_request_target 泄露 secrets | 仅 pull_request、最小只读权限、无 fork 写操作 | 停用 workflow、轮换受影响凭据、独立安全响应。 |
| README 镜像链接继续指向不可读地址 | M1 默认移除，恢复必须有探针和 runbook | 立即删除/标注，不等待镜像工程完成。 |
| 历史文档被全局替换破坏证据 | 搜索/修改范围显式排除 docs/迭代计划 historical | 回退唯一拥有的当前文档修改，保留历史目录不动。 |
| 把治理上线误报为 1.0/生产可用 | Readiness seal 保持 fail-closed；final-report 单列未完成块 | 纠正公开文档和状态，不发布、不打 tag。 |

## 9. 完成定义

本迭代仅在以下条件同时满足时才可归档：

1. D0-D4、D6 已签署；D5 有可复核的 not-triggered 或独立后续 issue。
2. M1 修复了 main 路由、MAINTAINERS 缺失、过时 public API fixture 和失效 Gitee 指引；历史快照未被批量改写。
3. M2/M3 的 manifest、比较器、风险分类和社区文件测试均已通过，且 required check 不依赖路径跳过。
4. M4 已用真实 API 和三类 PR 演练证明 master/dev 的实际设置；任一 pending-evidence 均已清零或被明确阻止上线。
5. 单维护者例外（如仍需要）有负责人、24 小时证据、到期日和复审记录，且 final-report 明说其不是双人审批。
6. 发布、Pages、镜像描述与当前实际一致；没有创建公开 release/PyPI 发布来“证明”计划。
7. 已完成四周指标复盘，并以实际证据把 0041 从 active 转为 historical。

满足上述条件只代表 PR 治理迭代完成；它不改变 docs/quality/1.0-readiness.md 的总体 blocked 状态，也不构成生产、合规或发布认证。
